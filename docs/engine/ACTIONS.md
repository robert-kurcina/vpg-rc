# Shared legal-action API — experimental B4M compatibility boundary

`core/actions.js` exports `legal(context, query)` and `execute(context, action)` for human/AI use. For now it executes **only** the verified Battle for Moscow scenario through the pre-existing Oberlabs-compatible adjudicator. The other historical registrations deliberately fail closed.

Inputs must supply `scenarioId`, `engine`, `config` (the B4M compiled scenario), `state`, `actor`, and the **actual UI phase name** (`setup`, `reinforcement`, `replacement`, `special`, `combat`, `combat-resolution`, or `movement`). The context phase must equal `state.phase`. `usedUnitIds` is an optional list for UI-moved/committed unit restrictions and is not yet stored in the engine state itself.

`legal` enumerates movement destinations, replacement choices, reinforcement destinations, and validates a known-die combat preview. `execute` consumes a typed action and returns `{ok,state,result}` on success; for an illegal player action it returns `{ok:false,state:originalState,reason}`. Structural errors (unsupported scenario, wrong actor or phase) throw. Committed actions clone the state first, preserving the caller's state on rejection and permitting Undo/event replay. Combat requires a **previously committed explicit die**; it never silently consumes the RNG. The UI is still responsible for die commitment before presenting outcome-dependent choices.

Available actions are setup placement/confirmation, normal and special movement, replacement (including budget count), Shock reinforcement, battle preview, and battle resolution. The battle queue, die commitment, phase transitions, general solo-AI conversion, and special historical micro-rules are **not** migrated. Do not route the shipping browser through this API until those state/UX boundaries have parity tests. This is not a replacement for the Oberlabs UI.

**Critical limitations:** `usedUnitIds` and battle-declaration reservations are presently owned by the UI, not the shared game state. A malicious client that supplies an inaccurate context can omit them. The existing B4M resolver is the authority for attack effects; this wrapper adds explicit phase/side gating, not full enforcement of an entire turn. Do not claim the shared API enforces complete simultaneous combat declaration or all legal-action invariants until those are migrated and tested. Phase policy and action types will eventually derive from each validated scenario rather than being hardcoded as a B4M compatibility adapter.
