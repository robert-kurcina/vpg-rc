## Development operating policy

- A development increment should deliver a meaningful rule, strategy or playable capability; group related fixes, tests and documentation. Do not create serial audit-only releases. Avoid generating planning-only releases.
- Use existing evidence unless changed code, a concrete defect, or a milestone exit requires retesting. No repeated full replay matrices for unrelated changes. Historical v318 hash mismatch remains archival unless it reveals a current gameplay defect; preserve the original evidence.
- Tests must support delivery: focused regression for changed behavior, integration at milestone boundaries, broader regression before a substantive distribution. Record actual failures/timeouts and distinguish cumulative evidence from current-version tests. No claims from unfinished runs.
- Track DONE/WIP/PLANNED/DEFERRED/REJECTED; keep active plan short. Move completed details to existing audit/provenance records, not a growing front-loaded checkpoint log. Maintain a concise change summary, remaining blockers and next deliverable in each package.
- Work on independent tasks when a test or source ruling blocks one item; do not repeatedly revisit settled decisions. No new architecture unless a specific demonstrated defect requires it. Report decisions needing user approval rather than silently modifying historical semantics.
- Preserve all five scenario configurations, approved artwork and source provenance. Do not use image generation or web images as game evidence. Browser-only shared architecture remains mandatory.
