## 1. Decisions and invariants

1. **B4M is the migration reference.** Preserve and test the existing Oberlabs-compatible experience in `legacy/`, including human vs AI and AI vs AI. Where the Oberlabs implementation conflicts with `b4m-rules.pdf` on the **CRT, mud replacements/mud behavior, or victory conditions**, retain the Oberlabs behavior and record the disagreement explicitly. Do not silently make the PDF authoritative for those cases.
2. **Single shared CRT matrix for the five historical configurations.** Use `rules_profiles/shared-crt.json`, verified against the supplied Arduous, Leningrad and Kiev CRT images; Odessa inherits Kiev's chart. The *resolver* and *result codes* are shared; combat modifiers and consequences remain subject to each game's rules.
3. **Single source of truth for action legality.** Human UI, AI, simulations and replay call the same rules evaluator. AI may use a separate evaluation/scoring policy, never a separate legality or combat resolver.
4. **Terrain registry is universal; enabled rows are scenario-specific.** Open, Forest, Swamp, City, Major City, Fortification, River, Major River, Railroad, Lake, Sea and Coast have stable feature IDs. A feature with no gameplay relevance to a scenario is omitted from its generated Terrain Effects Chart (TEC), not erased from the registry.
5. **Microrules are independently configurable.** Eligibility, costs, strength factors, rounding, odds shifts, support, retreats, ZOC and replacements are distinct operations. Absent, disabled, and enabled-with-zero-effect must stay distinguishable. A Major River must not accidentally inherit an ordinary River penalty unless its profile explicitly requests it.
6. **Canonical faction vocabulary:** `german`/`axis` as scenario requires, `soviet` (not `russian`) in APIs and displays. Parse legacy `russian` values at import boundaries, preserve originals in historical source records and avoid duplicating faction IDs. Nationalities (German, Romanian, Hungarian, Italian, Slovak) are *not* collapsed into a single nationality because stacking and territory rules depend on them.
7. **Moscow is a Major City; Tula is also Major City in B4M** per the supplied B4M rulebook. Moscow-specific replacement and victory exceptions remain attached to Moscow rather than all Major Cities.
8. **Odessa extends Kiev; it does not stand alone.** Merge the Odessa overlay onto the Kiev rules profile, applying Odessa's explicitly overriding clauses. Do not copy Kiev rules into a second independent rulebook.
9. **Separate gameplay hexside topology from artwork.** Rivers, Coast, Lakes and Railroads may use authored SVG vectors for rendering, but movement/combat/ZOC depend only on certified semantic terrain and hexside records. Do not infer gameplay edges from decorative wavelets.
10. **No backend-for-frontend required.** Play, rules, AI and saves execute locally in the browser; a static HTTP server may serve JS/JSON/assets. Avoid server-only packages in the runtime core.
11. **Keep all five map presentations working.** Engine consolidation must not alter SVG coordinates, city locations, water visual authority or bitmap terrain rendering without an explicit map-change request.

Proposed source layout (paths to be created incrementally):

```
  movement.js          # movement cost, rail, ZOC and impassability
  combat.js            # strength stages, odds, support, CRT, losses
  retreat.js           # legal paths and post-combat choices
  setup.js             # unit placement and hidden/untried states

  victory.js           # predicates, city control and isolation
rules/profiles/
  battle-for-moscow.json
  arduous.json
  leningrad.json
  kiev.json
  kiev-odessa.overlay.json
rules/audit/
  b4m-manifest.json
  B4M-COMPLIANCE.md
  discrepancies.json
rules/tests/
  fixtures/            # captured legacy state/action/seed snapshots
  differential/        # legacy vs new engine tests
  historical/          # sourced scenarios and cross-game tests
```

Do not move all legacy code into these modules at once. Retain `core/engine.js`, `core/modules.js`, and `legacy/engine.js` as adapters until tests demonstrate the new kernel can replace each subsystem. Avoid one-off string-driven rule execution or arbitrary JavaScript evaluation from JSON. Use a finite, versioned set of **typed operators** with validated parameters.

### Public API

```js
validateAction(state, action, profile)  // {legal, violations:[{ruleId, reason, details}]}
evaluateAction(state, action, profile)  // legal alternatives, costs, odds, probabilities, consequences
applyAction(state, action, profile, rng) // {state, events, consumedRandomness}
legalActions(state, side, profile)      // AI/UI candidate enumeration
```

The evaluator is side-effect-free. `applyAction` may produce a new state or an explicit event list, but never silently mutate the caller's input. Randomness is injected and logged so combat and AI-vs-AI sessions are replayable. Store schema/profile version and the exact source-provenance manifest in saved games.

### Evaluation stages (not arbitrary priority order)

1. **Eligibility:** scenario, turn, phase, ownership, unit/hex legality, forbidden terrain and crossings.
2. **Movement:** base cost, edge modifiers, terrain cost, connected rail exceptions, weather, available points; stopping upon EZOC.
3. **Combat participation:** declaration commitment, side limits, one attacking unit per relevant hexside, untried revelation, eligible support.
4. **Per-unit strengths:** terrain/weather/edge multipliers and exact rounding policy; multiply in the rule-specified sequence.
5. **Raw odds:** sum strengths; defender strengths; floor and clamp to supported columns.
6. **Column shifts:** defender terrain, river condition, fortification, support; clamp after all eligible shifts.
7. **CRT:** look up `(finalOdds, die)` using `core/historical_crt.js` or its consolidated successor.
8. **Effects:** step losses, retreat decisions, EZOC damage, stacking, advance, control, fleet/counter state.
9. **Turn events:** replacements, reinforcements, phase changes, end conditions, victory.

Important: stages are a design baseline. The rule inventory may reveal required substage ordering. Preserve fractions until the relevant rule explicitly requires rounding. Do not claim all named operations are implemented in v316.

## 7. Test strategy and negative cases

- **Differential:** Existing B4M vs new kernel: exact normalized states, legal-action sets, costs, odds, CRT outputs, event ordering and random draws.
- **Property based:** No illegal stacking, no units outside valid cells, no action by the wrong faction/phase, no forbidden Lake/Sea crossing, no negative replacement budgets, no attacker reused across committed battles.
- **Metamorphic:** Swapping renderer theme/assets has zero effect on legal actions; alias normalization leaves combat identical; disabling a microrule removes only its documented effect; game-profile inheritance does not affect unrelated games.
- **Cross-game:** Ordinary River vs Major River; B4M restricted rail vs other games' 1-MP rail road rule; Arduous Major City no shift vs Kiev/Leningrad/B4M; Soviet-only fortifications vs other variants.
- **AI:** AI cannot propose illegal moves; uses exactly shared CRT probabilities; replayable seeded decisions; strategic-policy changes cannot change enforcement.
- **Browser:** Static hosting (not `file://`), worker execution, reload/save and deterministic replay without a BFF.
- **Presentation:** Golden SVG/PNG checks for all five maps; terrain geometry and visual wavelets never enter game action logic.

Avoid a brittle rule-count KPI as the sole metric. Report (a) applicable rule-clause coverage, (b) rule correctness against sourced tests, (c) AI-action legality, (d) scenario completeness, and (e) remaining known gaps separately.

## 8. Major risks, alternatives and mitigations

| Risk | Failure mode | Mitigation |
|---|---|---|
| PDF vs Oberlabs disagreement | Fixing B4M to the wrong interpretation | Recorded precedence and differential fixtures |
| Generic JSON grows into a programming language | Unverifiable condition/effect interactions | Versioned typed operators; add code modules only for irreducible mechanics |
| Oversplitting into microfunctions | Fragile ordering and unnecessary complexity | Reuse a small set of composable evaluators with explicit stages |
| Visual terrain treated as rules | Coast wavelets change legality or movement | Separate semantic topology and art geometry |
| AI takes shortcuts around rules | Illegal plans or wrong combat probabilities | Shared legal/evaluate/apply API; legality at commit boundary |
| Mutable state during evaluation | AI preview reveals hidden counters or alters future play | Pure evaluation, controlled revelation actions, immutable inputs |
| Non-determinism and stale saves | Unreproducible tournament results | Versioned rules, seed injection, event logs, migration tests |
| False compliance percentages | Broad section counted as implemented | Atomic, testable rule inventory and named unresolved clauses |
| Odessa copied from Kiev | Rule drift and override bugs | Typed overlay + conflict audit + inherited tests |
| Historical setup incomplete | Map looks playable but cannot start correctly | Per-game unit/setup/reinforcement acceptance gate |

## 9. Definition of done

A historical scenario is **rules-complete** only when:

- All mandatory source rules, charts, victory conditions and special exceptions are explicitly classified and tested or documented as an approved variance.
- Every UI and AI move/combat uses the same enforcement and outcome evaluator.
- All required initial deployments, units, hidden information, events and turn schedules are instantiated.
- Human vs human, human vs AI and AI vs AI can complete the scenario using only local browser code and static assets.
- Saved games are reproducible against a named rules-profile version.
- Map rendering and the shared five-map visual suite remain correct.
